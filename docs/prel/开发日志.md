**开发日志**

本次调试的是 `iozone` 在内核运行测试时动态链接库加载失败的问题。

最开始运行 glibc 版测试：

```text
run /glibc/iozone_testcode.sh
./iozone: error while loading shared libraries: libc.so.6: cannot open shared object file: No such file or directory
```

检查 `iozone` 的 ELF 信息后发现，它是动态链接程序，解释器为：

```text
/lib/ld-linux-riscv64-lp64d.so.1
```

依赖库包含：

```text
libc.so.6
ld-linux-riscv64-lp64d.so.1
```

测试文件系统中实际的库位于：

```text
/glibc/lib/libc.so.6
/glibc/lib/ld-linux-riscv64-lp64d.so.1
```

内核中的 `interp_path()` 已经对 ELF 解释器做了路径兼容，会把 `/lib/ld-linux-...` 映射到 `/glibc/lib/ld-linux-...`。但后续 `libc.so.6` 不是由内核 ELF loader 加载，而是由用户态动态链接器 `ld-linux` 通过 `openat` 查找。因此它仍然会访问 `/lib/libc.so.6`，导致找不到库。

解决方法是在内核 `sys_openat()` 中增加 ABI 运行库路径重映射：当当前进程来自 `/glibc/` 时，把 `/lib/...` fallback 到 `/glibc/lib/...`；当当前进程来自 `/musl/` 时，把 `/lib/...` fallback 到 `/musl/lib/...`。这样不用修改测试脚本，也能让动态链接器找到对应运行库。

随后测试 musl 版时又出现了新的问题。musl 版 `iozone` 的 ELF 解释器是：

```text
/lib/ld-musl-riscv64-sf.so.1
```

但测试文件系统中没有这个文件，只有：

```text
/musl/lib/libc.so
```

musl 的动态链接器通常就是 `libc.so` 本身，只是通过 `ld-musl-*.so.1` 这个名字访问。因此在 `interp_path()` 中增加了 musl fallback：如果 `/musl/lib/ld-musl-...so.1` 不存在，但 `/musl/lib/libc.so` 存在，就把解释器路径映射到 `/musl/lib/libc.so`。

解决这个问题时又遇到一次编译错误：

```text
error: cannot find macro `format` in this scope
```

原因是 `loader.rs` 使用了 `format!`，但内核 `no_std` 环境下没有引入 `alloc::format`。最终可以通过引入：

```rust
use alloc::format;
```

或者改用 `String::push_str()` 拼接路径解决。为了保持内核代码风格，更推荐不用 `format!`，直接手动拼接字符串。

**总结**

本次问题的根因是动态链接分为两阶段：

```text
内核 ELF loader 加载 PT_INTERP 指定的动态链接器
动态链接器再通过 openat 加载 libc、libm 等共享库
```

原来的内核只处理了第一阶段的解释器路径，没有处理第二阶段的运行库路径。因此 glibc 程序能启动动态链接器，但找不到 `libc.so.6`。

最终解决方案是：

```text
1. 在 interp_path() 中处理 ELF 解释器路径
2. 在 sys_openat() 中处理动态链接器后续访问的 /lib/... 运行库路径
3. 对 musl 增加 ld-musl-*.so.1 -> /musl/lib/libc.so 的 fallback
```

这样 glibc 和 musl 测试都可以在不修改测试脚本的前提下，从各自目录加载运行库，避免 ABI 混用。

**本次调试：glibc basic 测试 robust list 退出报错**

### 问题 1：exit robust list failed: BadAddress

测试 glibc 版 basic 用例时，进程退出阶段报 warn：

```
exit robust list failed: AxErrorKind::BadAddress
```

**根因分析**

glibc 在初始化时（`__pthread_initialize_minimal`）会调用 `set_robust_list` 系统调用，将 robust list head 地址（指向 pthread 结构体中的 `robust_head` 字段）注册到内核。进程退出时，`do_exit` → `exit_robust_list` 尝试通过 `vm_read` 读取该用户态地址。

关键问题：`execve` 替换了整个地址空间后，只清除了 `clear_child_tid`，**没有清除 `robust_list_head`**。如果新程序在 libc 初始化完成前就退出（或 libc 初始化失败），旧的 robust_list_head 地址指向已销毁的地址空间，导致 `vm_read` 返回 `BadAddress`。

**修复**

在 `src/kernel/src/syscall/task/execve.rs` 中，与 `set_clear_child_tid(0)` 并列，增加：

```rust
curr.as_thread().set_robust_list_head(0);
```

execve 之后旧的地址空间已失效，清空 robust_list_head 避免读到垃圾地址。新程序启动后 libc 会重新调用 `set_robust_list` 注册正确的地址。
