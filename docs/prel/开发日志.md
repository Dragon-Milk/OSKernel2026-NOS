# 内核开发日志

## 5.1 - 5.5：熟悉内核开发和测评机制

- 我们一开始从 GitHub 上克隆了内核基座 `StarryOS`，准备在此基础上完成比赛内核开发。
- 浏览初赛网站和官方测评仓库后，大致了解了测评方式：进入官方 Docker 镜像后执行 `make`，再用生成的内核运行官方磁盘镜像中的测试点。
- 当时看到的测评点包括 basic、busybox、cyclictest、iozone、iperf、libctest、lmbench、ltp、lua、netperf 等。
- 第一次本地运行时，最直观的问题是输出非常冗长，十几个测试点一起跑耗时也很长。如果每次都跑全量，很难判断是哪一个测试点造成失败。
- 因此我们先在 `dev` 分支上探索如何拆分测试入口，最后通过改写 `init.sh` 实现了按 profile 指定测试点。
- 拆分之后才比较清楚地看到：基座内核已经能满足一部分测试，但也有很多测试点直接 0 分。LTP 是综合测试，case 数量最多、分数占比也最高，于是我们决定先把非 LTP 测试点尽量修起来，LTP 放到后面集中处理。

## 5.6 - 5.9：构建环境与基础运行问题摸底

- 这一阶段主要是在摸清官方 Docker 环境、Rust 工具链、QEMU 和构建依赖。
- 一开始我们也怀疑过，某些问题是不是能通过官方磁盘镜像解决。后来确认磁盘镜像只影响运行时测试，不能修构建期缺失的工具或依赖。
- basic / busybox 早期有全零的情况。检查日志后发现镜像里没有 `/bin/sh`，而很多脚本默认依赖 shell。
- 最后修复脚本执行路径：根据脚本所在目录选择 `/musl/busybox sh` 或 `/glibc/busybox sh`。这个修复不算复杂，但它解决的是测试脚本能不能真正跑起来的问题。

## 5.12：busybox applet 兼容

- 后续又发现 busybox 脚本里会直接调用 `mkdir`、`rmdir`、`sleep` 等 applet，但镜像中并没有这些 applet 的独立链接。
- 一开始看日志很容易误判成内核 syscall 不支持，因为表现是测试脚本失败。但仔细看其实是用户态命令根本没找到。
- 因此增加了 exec fallback，让缺失的 applet 能重定向到对应 libc 目录下的 busybox。
- 这一阶段主要是给后面的测试清障：只有测试脚本能稳定执行，后面 syscall 的问题才有意义。

## 5.17 - 5.28：非 LTP 测试流程整理

- libc-test 中有一部分 case 会卡住，早期我们先做了比较窄的 skip，避免一个 case 阻断后续测试。
- 同时观察 RV / LA、glibc / musl 四种组合下 basic 和 busybox 的 START/END 输出，确认测评脚本是否能被评分器识别。
- 5.28 左右曾经临时加入过 LTP skip 机制，只输出 LTP 的 group START/END，不真正执行 LTP case。当时这样做不是为了最终逃避 LTP，而是为了先避免 LTP 拖垮其他测试点，方便单独观察非 LTP 得分。

## 5.28 - 5.31：cyclictest 修复

- cyclictest 是团队前期重点处理的测试点。最开始它虽然有输出，但基本拿不到分。
- 查看测评标准后，我们发现压力场景下会启动 hackbench，而 hackbench 大量 fork 时出现失败。继续查后发现 COW 页引用计数使用的是 `u8`，400 个进程共享同一页时有可能超过 255，于是把 COW 页引用计数从 `u8` 改成 `u16`。
- 修完后 cyclictest 可以完整输出，但性能距离目标还差很远，于是开始看定时器和调度。
- 一开始我们以为把 tick 从 100Hz 提到 1000Hz 后，延迟应该能明显降低。但实际 cyclictest 的 Avg 仍然很高，某些修改后甚至更差。这说明问题不只是 tick 粒度，而是硬件定时器没有对齐用户态 timer 的真实 deadline。
- 后来把硬件定时器改成 deadline-aware 重编程，而不是固定周期 tick。第一次尝试后 Avg 没有下降，反而从三百多微秒变成六百多微秒。
- 这个结果一开始很反直觉，因为我们确实更频繁地设置了定时器。后来才发现 IRQ handler 中先 `update_timer()` 再 `on_timer_tick()`，导致 timer wheel 里还残留已经过期的 timer，硬件被重编程到过去的时间点，产生连续伪中断。
- 之后调整 IRQ handler 顺序，先清理过期 timer，再设置下一次硬件中断。
- 还有一个比较隐蔽的问题是相位锁定。cyclictest 的周期和系统 tick 之间会形成固定相位差，如果新加入的 timer 没有立即影响硬件 deadline，延迟会长期稳定偏大。最后在 `TimerRuntime::add()` 中对最早 deadline timer 立即重编程，才把这个问题解开。
- 压力场景下还需要实时调度支持。cyclictest 会调用 `sched_setscheduler(SCHED_FIFO, priority=99)`，如果内核忽略这个调用，它就会和 hackbench 创建的大量普通任务一起轮转，延迟自然下不来。
- 因此实现了基础 RT 队列，支持 `SCHED_FIFO`，并补上 `sched_setscheduler`、`sched_getscheduler`、`sched_getparam` 等 syscall。
- 后面多线程 cyclictest 仍然不稳定，又发现 clone 出来的子线程没有继承父线程的 RT 优先级，于是修复了 RT 优先级继承。
- LoongArch + musl 下还有一个问题：glibc 下 cyclictest 能正常输出，musl 下报 `unable to get scheduler parameters`。一开始我们怀疑是 musl libc 本身的 stub 问题，因为反汇编里看到部分调度函数行为很可疑，这让我们一度觉得内核侧可能没法修。
- 后来重新从实际运行日志出发，确认 cyclictest 仍然依赖内核返回合理的 scheduler 参数，于是回到 `sched_getparam`、`sched_getscheduler`、`sched_setscheduler` 的兼容语义上。最终修完后，LA 下 `cyc-all` 的 glibc 和 musl 都能输出 END。

## 5.29 - 6.3：busybox、profile 和测试入口整理

- 这段时间也穿插处理了 busybox 中 `kill 10`、`which ls` 等 applet 查找问题。
- 增加了 `TEST_PROFILE` 机制，让 init 阶段可以根据 profile 选择测试路径。
- 6.3 左右增加 `ltp-score` profile，为后续单独观察 LTP 输出和评分格式做准备。
- 这时我们的思路已经比较明确：先把测试入口拆开，让每个测试点都可以单独跑，再逐个修。

## 6.6 - 6.9：profile 与 LTP batch 雏形

- 6.6 增加 `TEST_PROFILE=perf` 和相关 profile，用于性能测试路径。
- 从这个阶段开始，我们准备正式处理 LTP。刚开始也尝试过直接跑完整 LTP，但很快发现效率很低：日志太长，一个 case 卡住后后面的 case 完全没有输出，很难定位第一个错误点。
- 因此团队开始搭建 LTP 分批测试框架。
- 增加 `src/init/ltp-cases/` case 列表和 `tools/check_ltp_batches.py` 校验脚本。
- 增加 `TEST_PROFILE=ltp-batch`，支持 `LTP_CATEGORY`、`LTP_BATCH`、`LTP_LIBC`。
- 这样 LTP 就能被拆成 process、fs、mm-ipc、common-easy、deferred 等部分，每个部分再拆成多个 batch。这个设计后来成为我们团队分工的基础。

## fs / storage：团队推进的主线

### 6.9：LTP fs-01 与 close_range

- 团队开始定位 `close_range02` 和 fs-01 相关问题。
- 这一阶段还在不断清理调试日志，避免为了定位问题加的输出影响后续提交。
- RV glibc fs-01 构建通过，但此时 fs 的问题还只是刚开始暴露。

### 6.10：fs-01 基础环境与权限

- fs-01 首先暴露的是运行环境问题。LTP 中有些 case 会查 `/etc/passwd` 和 `/etc/group`，但镜像里缺少必要用户和组。
- 团队在 init 阶段补齐 `root`、`nobody`、`daemon` 等必要项，而且是幂等追加，不覆盖镜像已有内容。
- 还修复了 `mount(NULL, target, "tmpfs", flags, NULL)` 的参数处理。之前空 source/data 会被当作用户指针读取，导致 EFAULT。
- 随后开始补进程 UID/GID 状态，修复 `getuid/geteuid/getgid/getegid` 和 setuid 系列。
- `access/chdir/openat/chmod/chown` 也逐步接入 VFS 权限检查。
- 这一天的意义比较大：fs 开始从“能打开文件”进入到“权限语义要像 Linux”的阶段。

### 6.11：LTP 全批次运行能力

- 团队修复了 `LTP_BATCH=all`、`LTP_LIBC=both` 的调度逻辑。
- 这里也踩了一个坑：一开始把 all/both 设成默认值，结果普通运行也会默认跑全量 LTP，测试时间变长，还容易误以为 profile 没生效。
- 后来恢复默认值，只在命令行显式传参时才跑 all/both。
- 同时还修复了 vendor checksum 导致的构建失败。
- 这一步让每个 category 可以一次性跑完全部 batch，也为后续验证“某个模块整体能不能跑到 END”提供了基础。

### 6.11：RISC-V musl fs-09 openfile 卡死

- 当时 fs-09 中 `openfile` 在 RISC-V musl 下会卡住。
- 团队没有直接在完整 batch 里盲查，而是临时把 fs:09 收窄到 `openfile` 单个 case，建立复现。
- 定位完成后再恢复批次脚本。这种方法后面我们修 mm-ipc 和 net 时也借鉴了：先缩小范围，再修具体语义。

### 6.12：open/openat 与 mknodat

- 修复 `open/openat` 中 `O_CREAT` 访问模式解析。
- 增加 `mknodat` 对命名 FIFO 的支持。
- 这类问题很多时候不是 syscall 完全没实现，而是 Linux 边界语义没有对齐。

### 6.13：fs 多批次基础修复

- 定位 fs-13 中 `writetest` 崩溃，并修复用户栈溢出问题。
- 修复 `fsync03` 中 pipe / FIFO / socket 的 errno。
- 修复 `*at` 路径基准和参数校验。
- 修复第一批日志回归问题。
- 修复只读文件系统写保护相关语义。
- 这一阶段开始明显感觉到，LTP 的 fs 测试不是只测主路径，而是非常细地检查失败路径和 errno。

### 6.14：mount 与 fcntl 初步修复

- 修复第 2B 批挂载边界语义。
- 开始处理第三批基础 fcntl 语义。
- fcntl 这里一开始实现比较粗，很多命令只是简单返回成功，LTP 会立刻测出来。

### 6.15：preadv/pwritev 与 fcntl 回归

- 修复 `preadv2/pwritev2 offset=-1`。
- 修复 `F_SETLEASE` 回归问题。
- 修复定位/向量 I/O 基础错误语义。
- 修复 `pwrite append` 与 `truncate` 相关语义。
- 中间也出现过编译错误，需要先保证修改能过构建，再继续跑 case。

### 6.16：权限、硬链接、rename

- 修复 `RLIMIT_FSIZE`。
- 修复 setgid 与组继承，以及 mkdir setgid 继承。
- 修复 `O_NOATIME`。
- 修复 hard link 对象一致性和 cache 生命周期。
- 修复 rename 类型、权限与 sticky bit 语义。
- 这些修复都属于“文件系统对象生命周期和元数据一致性”问题，比单个 open/read/write 更复杂。

### 6.17：路径、stat、fcntl 深入

- 修复 getcwd 边界与已删除目录 getdents。
- 修复 stat 路径权限与 statx 参数校验。
- 修复 LA 下 lstat NULL 问题。
- 修复 open `O_NOFOLLOW`。
- 处理目录项、symlink、cwd 综合批。
- 团队开始设计并实现高级 fcntl / record lock 机制。
- record lock 是 fs 中比较复杂的一块，需要考虑 POSIX lock、OFD lock、区间合并拆分、close/exit 释放、阻塞等待等问题。

### 6.18：fcntl 收尾、xattr、mknod、immutable

- 高级 fcntl 做最终收尾。
- 调查 LA openfile 并发卡死。
- 整理高级 fcntl 验证前的工作区，避免把临时调试或无关修改带进去。
- 修复 xattr、mknod 与 immutable flag。
- xattr 一开始底层文件系统没有原生接口，因此采用高层 inode 级兼容存储，用 `(device_id, inode)` 作为 key，保证 hard link 能共享扩展属性。
- 还修复 append-only、只读挂载 unlink、procfs/linkat 等残留问题。
- 修复 getcwd ABI、directory nlink 以及 procfs 与 exec 环境阻断。
- 修复 `F_SETPIPE_SZ` panic。

### 6.19：LTP 环境与 open13

- 梳理 LTP kernel config 来源。
- 梳理 helper / resource / shell 路径。
- 修复 fs-09 `open13` 中 O_PATH fd errno。
- 处理 musl 下 O_PATH at-syscall 和 proc-fd 路径问题。
- 修复 Cargo vendor hidden-filter 问题。

### 6.20：storage-safe 收尾验证

- storage 方向一开始也想尽量全跑，但很快遇到 `fsstress`、`fs_racer`、`read_all` 等 case 导致 hang、panic 或环境污染。
- 后来团队调整策略：先做 `storage-safe`，保证能跑到 group END，再把危险 case 放到 diagnostic category 里单独摸底。
- 验证 RV / LA、glibc / musl 下 `storage-safe` 能跑到 group END。
- 日志中确认没有 `mkdir/basename/cat/sleep not found`、kernel panic 或 memory allocation failed。
- 这里的 skip 不是最终修复，只是为了避免一个高风险 case 阻断后面大量测试。

### 6.22：ltp-safe 与高风险 case 隔离

- 增加 `ltp_skip_case()`，跳过高风险 case，例如 `futex_cmp_requeue01`、`mmap-corruption01`、`mmap1`、`shm_test`。
- 一开始对 skip 也有争议，因为跳过看起来像逃避问题。但对于比赛测评来说，如果一个 case 直接 panic，后面几百个 case 都不执行，损失更大。
- 调整 `epoll-ltp`，从直接 skip 改为 timeout 后清理残留进程。
- 增加 storage diagnostic skip，跳过 `sendfile07`、`fs_racer*`、`fsstress`、`fsx-linux`、`growfiles`、`rwtest`、`read_all` 等危险 case。
- 建立 `storage-splice-candidate`、`storage-fsbind-candidate` 等用于摸底的 category。

### 6.23：busybox applet 与 runner 卡住问题

- 整理 `ltp-safe.txt`，加入更多 safe case。
- 精简 profile，保留 `stable`、`cyc-*`、`ltp-*`、`full-safe` 等必要入口。
- 为 `ltp-safe` 准备 busybox applet 链接，解决 `basename/cat/mkdir/sleep` 等命令找不到的问题。
- 这里也踩了两个 runner 自己的坑。
- 第一个是诊断日志写到了 stdout，而 case list 也是 stdout 管道传递的，导致 `[LTP-SAFE] batch-filter ...` 被当作 case 名执行，出现很奇怪的 missing case。
- 第二个是子进程继承了 case list 管道的 stdin，可能把后续 case 名读走，表现得像 LTP 卡住。后来给 case 执行加 `< /dev/null` 才解决。
- 这些问题说明，LTP runner 自己也需要像内核一样小心处理输入输出。

### 6.24：LTP_CASE_LIST 单 case 能力

- 完善 `LTP_CASE_LIST` 从 Makefile 到 init.sh 的传递链。
- 增加 `ltp-safe` profile，使其只跑 LTP safe，不跑 full-safe 里的非 LTP 部分。
- 用 `strings kernel-rv` 验证编译进内核的 `TEST_PROFILE=ltp-safe` 确实生效。
- `LTP_CASE_LIST` 后来对 net 修复非常关键，因为它允许我们直接指定几个 case，而不是每次都跑完整 batch。

## process / testb：团队推进的 LTP 主线

### 6.13：建立 process 分批测试框架

- process case 同时覆盖 `execve`、`clone`、`fork`、`wait`、`signal`、scheduler、uid/gid、pidfd 等内容，全量运行时很难定位问题，因此先拆成 01 到 15 批。
- 使用 `TEST_PROFILE=ltp-batch LTP_CATEGORY=process LTP_BATCH=xx` 单独验证各批次，以区分当前 batch 的实现问题和前序 case 的状态污染。

### 6.14：修复 execve / execveat

- 这一阶段集中修复 `execve` 和 `execveat`。当时路径权限、超长文件名和参数栈构造与 Linux 行为不一致，导致 `execve02`、`execve04`、`execve05` 等 case 失败或段错误。
- 后续补充文件名过长返回 `ENAMETOOLONG`、执行权限检查、用户栈参数构造，并增加 `execveat` syscall 分发，使 exec 系列能够进入稳定回归。

### 6.15：推进 clone / clone3 与身份状态继承

- process 批次继续推进到 `clone` / `clone3` 和基础身份类 syscall，主要暴露参数校验以及 fork/clone 后状态继承不完整的问题。
- 修复时补充部分 clone flag 检查，并让子任务继承调度参数、nice、personality、uid/gid 等必要状态，避免父子进程看到的身份和运行状态不一致。
- 同时修复 `getgroups` 非法 size 返回 `EINVAL` 等细节。LTP 还会检查失败后用户数组是否保持不变，因此不能只返回一个大致正确的错误码。

### 6.16：补齐 priority、personality 与时间语义

- 第 04 到第 06 批开始补充 `gettimeofday` 写回 timezone、`getpriority` / `setpriority`、personality 保存与继承，以及 `nanosleep` / `leapsec` 中的时间差溢出处理。
- `nice` 系列暴露了一个容易忽略的问题：glibc 会对内核返回的 raw priority 再做一次转换，所以内核侧 `getpriority` 应返回 `20 - nice`，不能直接返回用户看到的 nice 值。

### 6.17：修复 signal、prctl 与 scheduler

- 第 07 到第 08 批集中处理 signal、prctl 和 scheduler，包括 signal action reset、部分 prctl 行为、scheduler 参数接口，以及 `sched_get_priority_min/max` 的边界语义。
- 这一阶段开始出现 `kill10`、`pidfd_open01`、`sched_get_priority_min01` 等 case 单独运行可以通过、组合运行却偶尔卡住的现象。这说明问题不一定在当前 case，也可能是前面的测试留下了等待状态或残留任务。

### 6.18：完善 credentials、groups 与 job control

- 第 09 到第 11 批主要处理 credentials、groups 和 job control，补充 uid/gid/resuid/resgid 继承与权限检查、process group 注册、kill 权限及进程组发信号。
- 这些 case 很多并不是测试 syscall 主路径，而是在检查“谁有权限向谁发送信号”“子进程继承了哪些身份”“`setpgid(pid, 0)` 是否正确注册进程组”等 Linux 规则。

### 6.19：修复 wait、signal wait 与资源回收

- process 后半段继续补充 `wait4` / `waitid`、signal wait、时间相关 syscall、`/proc` 信息和部分 mmap / loader 行为。
- `waitid05`、`wait401`、`sigwait01`、`sigwaitinfo01` 等 case 的关键并不是简单返回成功，而是子进程退出状态、可等待状态、信号唤醒和资源回收必须一致，否则 LTP 框架本身会停在等待阶段。

### 6.20：从全量运行转向稳定集合

- process 也采用了与 storage-safe 类似的策略：稳定通过的 case 保留在各批次中，可能挂住或依赖较大缺失子系统的 case 暂时移入 non-pass 列表。
- 目标从“一次性全量硬跑”调整为先保证已通过 case 能稳定完成，再通过单 case 或小批次逐步补齐 Linux 语义。

### 6.21：排查随机卡住与输出格式

- process 批次跑到后面时，最麻烦的问题变成随机卡住：有时停在 `abort01`，有时停在 `wait401`、`signal02`、`clock_nanosleep04` 或 `setregid03`，但单独运行又不一定能够复现。
- 后来判断很多问题并不是单个 case 的稳定死锁，而可能来自进程资源、信号等待或残留任务没有完全清理，使后续 case 在 fork、wait 或 signal 路径上被拖住。
- 同时恢复了 LTP runner 的外层固定输出格式。旧评测脚本依赖 `FAIL LTP CASE xxx : code`，即使 code 为 0 也可能必须保留该前缀；如果改成 `PASS LTP CASE xxx : 0`，反而可能导致平台计分脚本识别不到通过项。
- 这一轮之后，process 从“经常随机卡住，难以判断是哪一个 syscall 的问题”逐步转变为“可以按 batch 复现、按 syscall 修复、按稳定列表回归”。

### 6.22：隔离高风险 process case

- process 列表继续收敛：保留稳定通过项，移出可能长期阻塞、依赖完整调度权重、终端 hangup 或更完整 pidfd 行为的 case。
- 这种隔离并不是把问题隐藏起来，而是避免一个未完成语义阻断后面已经能够得分的测试。

### 6.23 - 6.24：将隔离经验用于 testb / Part-B

- testb / Part-B 同时包含 process、mm-ipc 和 security case。若某个测试程序读取 stdin 或留下子进程，会表现为运行数量减少、提前结束，甚至卡在看似无关的 case。
- 后续开始使用 `LTP_CASE_LIST` 整理 Part-B，不再先全量硬跑，而是从日志中确认 glibc 和 musl 都能通过的 case，再保存稳定集合。
- 统计时不能只看外层 `FAIL LTP CASE` 文本，因为旧 runner 成功时也会输出 `FAIL LTP CASE xxx : 0`，最终仍需根据返回值 `: 0` 判断通过。

### 6.25：收敛 glibc / musl 共同通过集合

- `testb.log` 中 glibc 和 musl 各运行了 389 个 case，其中 glibc 有 88 个返回 0，musl 有 80 个返回 0。
- 两端共同通过的稳定交集为 80 个。为了让 testb 先稳定拿到确定分数，Part-B 列表先收敛到这 80 个 case，并重新生成 `ltp-cases.sh`。
- 未通过项没有被永久删除，而是暂时移出稳定列表，留待后续通过 `LTP_CASE_LIST` 单独定位和修复。

### 6.26：清理随机残留进程

- testb 全量运行仍可能提前退出或随机卡在不同 case。结合 process 阶段的经验，重点怀疑残留子进程、stdin 管道继承和资源没有回收。
- runner 为每个 case 增加运行前进程快照；case 结束或超时后重新扫描 `ps`，对本轮新增但仍然存活的进程先发送 `TERM`，等待后再发送 `KILL`，并输出 `[LTP-CLEANUP]` 日志。
- 普通 LTP case 和 `epoll-ltp` 的执行都补上 `< /dev/null`，防止测试程序消费 case list 管道。
- 修改后，每个 case 的隔离性得到改善。即使某项超时或遗留子进程，也会在下一项开始前被清理；testb 当前只保留 glibc / musl 均确认通过的稳定集合，随机卡住和提前退出的概率随之下降。

## mm-ipc：团队推进的 LTP 模块

### 6.10 - 6.12：mm-ipc 批次摸底

- 在 LTP batch 框架搭好后，团队开始推进 `mm-ipc` 部分。
- 一开始没有急着追求所有 case 通过，而是先确认每个 batch 能不能跑完。
- 当时主要看 `TPASS`、`TFAIL`、`TBROK`、`TCONF`。其中 `TBROK` 往往比 `TFAIL` 更麻烦，因为它说明测试可能没法正常继续。
- 一开始团队也会盯着第一个 panic 修，但后来发现有些 panic 修完后，后面还有大量 TFAIL，收益不一定高。
- 后来策略改成先找 TPASS 提升明显的批次，尤其是 SysV IPC 集中的 07、09、05 批。

### 6.12 - 6.13：第 03 批与内存相关问题

- 第 03 批里遇到过 `mincore01`、`mmap001` 等内存相关 case。
- 有些 case 运行时间很长，比如 `mmap001` 加默认参数时容易让人以为卡死。
- 当时我们也试过给压力 case 加参数限制，先保证批次能跑完，再判断内核语义本身的问题。
- 这件事让团队意识到，LTP 中有些 case 本身就是压力测试，不能只凭“输出很多”或“跑得久”判断失败，要结合是否超时、panic 或最终返回值判断。

### 6.13：第 07 批 semaphore 修复

- 第 07 批主要集中在 SysV semaphore。
- 一开始 `semget01/02/05`、`semop01/02/03`、`semctl01/02` 等 case 有不少 `TBROK`。
- 修复重点包括信号量集合创建、key 查找、`IPC_CREAT`、`IPC_EXCL`、权限检查、错误码返回，以及 `semop` 操作数组的处理。
- 这部分修复很有收益，因为 semaphore 系列 case 比较集中，改对一类语义后多个 case 都会一起改善。
- 最后第 07 批基本能稳定通过，这也是 mm-ipc 阶段最明显的一次提升。

### 6.14：第 09 批 shared memory 修复

- 第 09 批主要是 shared memory，包括 `shmget`、`shmat`、`shmdt`、`shmctl`。
- 这里踩过一些比较细的坑。例如 `IPC_PRIVATE` 应该每次创建新对象；已有 key 加 `IPC_CREAT | IPC_EXCL` 时应该返回正确错误；`shmdt` 对非法地址不能 panic，而是返回 errno。
- shared memory 还涉及对象删除后的生命周期。对象被标记删除后，已经 attach 的进程仍然可能继续使用，这一点和普通“删除立即消失”的直觉不一样。
- 修复过程中还遇到 Rust 类型问题，例如 `IPC_CREAT`、`IPC_EXCL` 和 `shmflg` 类型不一致导致编译失败。
- 后续 `shmctl04/07/08`、`shmdt01`、`shmget02/05/06` 等 case 逐步通过。

### 6.14 - 6.15：第 05 批 message queue 修复

- 第 05 批主要集中在 message queue。
- 修复对象包括 `msgget`、`msgsnd`、`msgrcv`、`msgctl`。
- 这部分问题集中在消息长度、队列容量、消息 type、用户态结构体读写和错误码。
- 有些 case 不是功能完全没实现，而是 errno 不对。改完一处后，另一个 case 又会暴露新的边界，只能反复跑日志确认。
- 后续 `msgctl06`、`msgget04/05`、`msgrcv05/06`、`msgsnd05/06` 都有明显改善。

### 6.15 前后：mm-ipc 小结

- mm-ipc 的修复中最明显的体会是：SysV IPC 的主路径其实不难，难的是资源生命周期和错误码。
- LTP 会构造很多非法参数、重复创建、删除后访问、权限不匹配、用户地址错误等情况。
- 如果只是让 `shmget`、`semget`、`msgget` 这些调用“能成功”，远远不够。
- 最后我们主要靠单批次反复回归确认：第 07 批 semaphore、第 09 批 shared memory、第 05 批 message queue 都有比较明显的提升。

## net：基于 LTP_CASE_LIST 的冲刺修复

### 6.15 前后：net case 摸底

- net 部分开始时，我们也想过直接扫一大批 case，但很快发现 socket 相关测试很容易卡住。
- 如果没有单 case 能力，定位效率非常低，因为一个 case 阻塞后后面的 case 就没有输出。
- 因此后面主要依赖 `LTP_CASE_LIST`，一次只跑几个目标 case。
- 我们从 `net-*.txt` 和 deferred 列表里挑选 TPASS 密度较高的 case，优先修那些能较快转化成得分的点。

### 6.15 前后：建立 confirmed 列表

- 修 net 的过程中，经常遇到一个问题：某个 case 这次过了，但后面改 socket 代码时会不会又把它改坏。
- 为了避免每次都重新翻日志，我们建立了 `net-confirmed-pass.txt`。
- 这个文件不是一开始设计好的，而是在反复回归中自然需要出来的。
- 之后每修完一批 net case，就把确认稳定通过的 case 加进去，再用 confirmed 做小范围回归。

### 6.15 前后：send / recv 与 MSG_MORE

- `send02` 一开始看起来像普通 send/recv 问题，但后来发现关键在 `MSG_MORE` 和阻塞行为。
- 如果只是让 send 返回成功，case 仍然可能卡住或 fail。
- 后续在 socket 发送路径中补充对相关 flag 的处理，并注意 `MSG_DONTWAIT` 等非阻塞语义。
- 这类问题说明 net 测试经常不是测主路径，而是测 flag 组合下的边界行为。

### 6.15 前后：sendmmsg / recvmmsg

- `sendmmsg` 和 `recvmmsg` 系列是批量消息接口，比普通 send/recv 更容易出错。
- 修复重点包括用户态 mmsghdr 数组读写、每条消息长度、部分成功时的返回值、flags 和 timeout。
- 一开始我们也遇到过“看起来应该过，但日志里仍然 fail”的情况。后来发现是返回值数量和用户态写回不符合 LTP 预期。
- 修完后，`sendmmsg01`、`recvmmsg01` 等 case 加入 confirmed 列表。

### 6.15 前后：accept 与错误路径

- `accept03` 这类 case 不是测正常连接，而是测错误路径。
- LTP 会构造非法 fd、特殊 fd 或不支持的参数，要求内核返回正确 errno。
- 这类 case 修起来不像功能开发，更像对 Linux 行为补细节：失败也要失败得正确。
- 修完后，confirmed 列表逐步扩大，net 部分有了一组可以稳定回归的 case。

### net 小结

- net 阶段最大的经验是不要一上来跑全量。
- socket 测试太容易阻塞，必须依赖小批量 case 和 confirmed 回归。
- `LTP_CASE_LIST` 在这里非常有用，它让我们能快速指定几个目标 case，修完就验证，不需要反复修改 batch 文件。

## 总结

- 这段时间的开发大致经历了三个阶段：先修非 LTP，尤其是 cyclictest；再通过 LTP batch 框架把 LTP 拆开分工；最后用 `LTP_CASE_LIST` 做单 case 冲刺。
- 团队主要完成了 LTP 框架和 fs / storage 方向的大量修复，这部分解决的是“怎么测、怎么分工、怎么稳定跑完”的问题。
- 团队在 cyclictest、mm-ipc 和 net 方向也进行了持续修复。cyclictest 更偏定时器和调度；mm-ipc 更偏 SysV IPC 资源生命周期；net 更偏 socket flag 和错误路径。
- 最大的体会是，到了比赛后期，很多问题已经不是“有没有这个 syscall”，而是“边界行为是否像 Linux”。错误码、权限、资源生命周期、阻塞行为和测试脚本环境，都会直接影响最终分数。
